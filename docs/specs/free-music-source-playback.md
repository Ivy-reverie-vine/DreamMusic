# 免费音乐源与可靠在线播放规格

状态：已发布到 GitHub Issue #1，待实现拆分

## Problem Statement

用户希望 DreamMusic 在不依赖付费会员的前提下获得更多可播放音乐。

当前在线来源主要是 `api-enhanced`。当普通播放 URL 为空时，HarmonyOS 客户端会直接判定为无版权或需要会员；客户端不会调用解灰换源。NightDream 中虽然存在 QQ、酷狗、酷我和咪咕的顺序匹配逻辑，但该逻辑属于服务端下载任务，不属于客户端普通在线播放链路。

当前还存在第二个问题：部分 URL 即使已经从 NightDream 返回，也可能在 HarmonyOS AVPlayer 初始化、重定向、请求头、Range 请求或 URL 有效期环节失败。现有播放器只记录概括性错误，无法区分 URL 解析失败、URL 传输失败、AVPlayer 初始化失败和音频播放失败。

本规格要解决的是：

1. 在 NightDream 内建立可替换的免费音乐来源调度能力。
2. 将来源搜索、元数据、歌词、封面和播放解析拆成可独立验收的能力。
3. 提高普通在线播放的成功率，减少对单一 `api-enhanced` 解灰链的依赖。
4. 在不破坏当前 HarmonyOS 客户端和本地音乐库的前提下逐步扩展来源。
5. 让播放失败具备可定位的阶段信息和来源健康度信息。

## Solution

NightDream 增加统一的来源注册、能力适配和播放调度层。DreamMusic 客户端继续只访问 NightDream，不直接访问第三方音乐平台。

首批评估两类来源：

- 国内多平台：以 Meting adapter 作为 POC 边界，评估 QQ、酷狗、酷我等平台的搜索、元数据和播放 URL 能力。
- 免费授权或开放音乐：评估 Audius、Jamendo 等具有公开 API 或明确授权边界的来源，作为合法免费音乐补充。

YouTube、ytmusicapi 和 yt-dlp 只作为隔离 POC 候选，不作为首批生产播放来源。

整体调度流程为：

1. NightDream 完成账户鉴权、绑定检查、限流和参数校验。
2. `SourceRegistry` 提供已启用的来源和能力声明。
3. `MusicOrchestrator` 根据请求能力、来源优先级和健康状态选择来源。
4. 各 adapter 将外部响应转换为统一内部模型。
5. 调度器执行超时隔离、部分成功、去重、排序和失败降级。
6. `PlaybackResolver` 返回短时有效的播放引用或播放 URL。
7. 如果直接 URL 无法稳定被 AVPlayer 使用，再启用受控的签名媒体代理。

第一阶段保留当前公共 API 和客户端数字 ID 契约。新来源先用于服务端 POC 和受控测试，不直接进入当前客户端播放流程。

## User Stories

1. 作为 DreamMusic 用户，我希望普通歌曲不再完全依赖单一网易云来源，以便在来源不可用时仍有机会播放。
2. 作为 DreamMusic 用户，我希望搜索结果能够标识其来源关联，以便播放、歌词和封面请求不会使用错误的平台 ID。
3. 作为 DreamMusic 用户，我希望来源暂时不可用时系统自动尝试其他已启用来源，以便减少手动重试。
4. 作为 DreamMusic 用户，我希望一个来源变慢时不会拖住全部搜索和播放，以便播放器保持响应。
5. 作为 DreamMusic 用户，我希望播放失败时看到可理解的失败提示，而不是只看到笼统的网络错误。
6. 作为 DreamMusic 用户，我希望成功拿到播放 URL 后能够真正交给 HarmonyOS 播放器播放，而不是只在服务器日志中显示成功。
7. 作为 DreamMusic 用户，我希望播放链接过期时系统能够重新解析，而不是永久复用失效 URL。
8. 作为 DreamMusic 用户，我希望歌词、封面和播放能力可以独立降级；缺少歌词不应阻止播放。
9. 作为 DreamMusic 用户，我希望本地音乐在所有在线来源失败时仍可正常播放。
10. 作为 DreamMusic 用户，我希望在线歌曲成功入库后能够转换为普通本地音轨，而不因来源变化破坏本地音乐库。
11. 作为 DreamMusic 用户，我希望免费来源的音质和授权边界能够被如实反映，不把低码率或受限资源伪装成高音质资源。
12. 作为 DreamMusic 用户，我希望系统不会要求我把第三方平台 Cookie 上传到 HarmonyOS 客户端。
13. 作为 DreamMusic 用户，我希望来源故障不会导致账户退出、网易云绑定丢失或本地播放状态丢失。
14. 作为 DreamMusic 用户，我希望来源切换不会改变四个一级入口和当前播放器交互。
15. 作为 DreamMusic 用户，我希望来源选择默认由服务端处理，不必先理解各个平台的 ID 和认证规则。
16. 作为 NightDream 运维者，我希望能够单独启用或关闭某个来源，以便快速灰度和回滚。
17. 作为 NightDream 运维者，我希望每个来源都有独立超时、并发限制和熔断状态，以便一个来源故障不会拖垮整个服务。
18. 作为 NightDream 运维者，我希望能够看到各来源的搜索成功率、播放解析成功率、延迟和错误类别，以便定位“解灰慢”和“播放器失败”。
19. 作为 NightDream 运维者，我希望日志不会记录 Cookie、Token、签名和完整带参数媒体 URL，以便降低凭据泄露风险。
20. 作为 NightDream 运维者，我希望播放 URL 缓存有明确 TTL，以便不把过期地址当成永久资源。
21. 作为 NightDream 运维者，我希望来源 adapter 可以独立替换，不需要修改客户端页面和播放器。
22. 作为 NightDream 运维者，我希望 Meting、Audius、Jamendo 等外部依赖被隔离，以便替换运行时或服务时不影响核心网关。
23. 作为 NightDream 运维者，我希望下载任务继续使用现有计费、退款和任务状态，以便新增普通播放来源不会改变下载业务。
24. 作为 NightDream 运维者，我希望普通播放和服务端下载拥有不同的能力声明，以便避免误把下载兜底当作普通播放契约。
25. 作为 NightDream 开发者，我希望能用 fake adapter 重现超时、空 URL、格式错误和部分成功，以便不依赖真实第三方服务开发调度器。
26. 作为 NightDream 开发者，我希望每个 adapter 都遵守同一组契约测试，以便新增来源不会降低统一质量标准。
27. 作为 DreamMusic 开发者，我希望当前 `api-enhanced` 搜索和 `/song/url/v1` 行为保持兼容，以便旧客户端无需立即升级。
28. 作为 DreamMusic 开发者，我希望未来可以通过版本化 `mediaRef` 支持字符串来源 ID，以便不破坏当前数值型歌曲 ID。
29. 作为 DreamMusic 开发者，我希望播放器能够区分 URL 解析、URL 传输、AVPlayer 初始化、prepare 和实际 playing 阶段，以便建立真实故障反馈环。
30. 作为项目维护者，我希望任何新增来源都经过稳定性、合规性、凭据安全和回滚验证后再开启生产流量。

## Implementation Decisions

### 来源与能力

- 每个来源必须声明自身支持的能力：搜索、详情、歌词、封面、普通播放和服务端下载解析。
- 未声明的能力必须返回明确的能力缺失错误，不允许 adapter 静默伪造成功。
- Meting 只能作为内部 adapter 或隔离服务使用，不能成为 DreamMusic 公共领域模型。
- Audius 和 Jamendo 作为免费授权/开放音乐来源候选，必须保留来源许可证或授权元数据。
- YouTube/yt-dlp 不进入首批生产播放链；如进入 POC，必须运行在独立 worker 或 sidecar 中。

### 调度与降级

- `api-enhanced` 继续是现有来源和兼容默认路径。
- 新来源默认关闭，只能通过服务端配置、测试账号或灰度开关启用。
- 来源请求采用并发预算和总截止时间，不采用无限串行重试。
- 每个来源拥有独立超时、速率限制、并发上限和熔断状态。
- 搜索允许部分成功；播放解析优先返回第一个通过可用性校验的结果。
- 所有来源失败时返回统一的来源不可用错误，不暴露第三方内部错误和凭据。
- 播放 URL 只能短时缓存；缓存必须按来源、歌曲引用和有效期隔离。

### 歌曲引用与公共契约

- 内部歌曲引用由 `source`、`sourceId` 和 `kind` 组成。
- 元数据、歌词、封面和播放解析必须沿用同一个歌曲引用。
- 当前客户端继续使用数字歌曲 ID和既有公共响应，不直接接收新来源字符串 ID。
- 客户端多来源能力通过版本化的 `mediaRef` 契约引入，不把字符串 ID 写入现有数字 `id`。
- 新来源在客户端契约升级前只用于服务端 POC、内部验证或受控实验。

### 播放传输与故障诊断

- NightDream 首选返回短时有效的可播放引用，不默认代理全部音频字节。
- 如果第三方 CDN URL 在 HarmonyOS AVPlayer 上因重定向、Range、请求头或有效期问题失败，再增加签名媒体代理。
- 媒体代理必须支持鉴权、短时签名、Range 请求、Content-Type、Content-Length、重定向和上游错误映射。
- 媒体代理不得把完整上游 URL、Cookie 或 Token 写入普通日志。
- 播放链路必须记录脱敏的阶段事件：解析开始、解析完成、URL 交给客户端、AVPlayer initialized、prepare、playing、error。
- 记录来源 ID、能力、耗时、错误类别和状态，不记录完整媒体 URL。

### 客户端与本地音乐库

- 不新增来源选择 UI，不改变四个一级入口。
- 在线失败不得影响本地音乐库、队列、播放模式和后台播控。
- 在线音轨仍然可以先作为瞬态条目播放，成功下载并完成元数据处理后再替换为本地音轨。
- 新来源的本地入库需要使用来源无关的本地实体标识，不能继续假设所有来源都是网易云数字 ID；该改造属于客户端契约阶段。
- 普通播放不调用服务端下载任务，不改变下载计费和退款逻辑。

### 安全、合规与运行边界

- 客户端不接受任意上游 Cookie、代理地址或 extractor 参数。
- 第三方凭据只存放在受控服务端配置中。
- 不设计绕过 DRM、访问控制、会员限制或服务条款限制的流程。
- 免费来源必须区分“免费使用 API”与“可合法播放/下载的音乐内容”。
- 生产开启来源前必须完成来源条款、部署地区、内容授权和数据处理评估。

### 实施顺序

1. 先建立播放链路诊断和 fake adapter 反馈环。
2. 抽取 `api-enhanced` adapter，确保现有公共行为不变。
3. 接入 Meting adapter 做国内多平台元数据和播放解析 POC。
4. 接入 Audius 或 Jamendo 之一，验证免费授权来源的完整播放闭环。
5. 对直链播放失败样本评估是否需要签名媒体代理。
6. 只有当来源引用、播放引用和本地入库模型稳定后，才升级 HarmonyOS 客户端 `mediaRef` 契约。

## Testing Decisions

### 测试原则

- 优先测试调度器和网关的外部行为，不测试 adapter 内部实现细节。
- 真实第三方服务只用于隔离 POC 和验收，不作为单元测试依赖。
- 每个测试必须能区分成功、空结果、来源超时、URL 为空、URL 过期、AVPlayer 初始化失败和实际播放失败。
- 所有网络测试使用可控 fixture 或本地 stub，避免依赖用户 Cookie 和不稳定的真实账号。

### NightDream 测试

- adapter 契约测试：正常搜索、空结果、字段缺失、错误 JSON、超时、429、认证失败和能力缺失。
- 调度器测试：默认来源兼容、并发来源、部分成功、全失败、去重、排序、缓存和熔断。
- 播放解析测试：短时缓存、URL 重新解析、来源切换和过期地址拒绝。
- 安全测试：Cookie、Token、签名、完整 URL 和上游请求头不进入响应与日志。
- 网关集成测试：401、403、301、429、502、绑定失效和来源开关行为。
- 回归测试：下载任务计费、退款、任务状态、文件获取和普通播放边界保持不变。

### HarmonyOS 测试

- 纯逻辑测试验证在线歌曲引用、瞬态音轨和失败状态转换。
- 设备测试验证 HTTP URL 的重定向、Range、HTTPS、音频 Content-Type、AVPlayer 初始化、prepare 和播放状态。
- 设备测试验证 URL 失败后本地音轨仍可播放，且不会污染队列和本地数据库。
- 设备测试验证后台播放、锁屏播控和短时 URL 重新解析。
- HAP 构建和 Hypium 测试通过后，仍需真机验证第三方 CDN 和媒体代理行为。

### 验收标准

- 所有新来源关闭时，现有 `api-enhanced` 行为和客户端解析结果不变。
- 一个来源超时不超过总截止时间，且不会阻塞其他来源。
- 新来源失败不会导致客户端登出、绑定失效或本地播放中断。
- 成功返回的播放引用能够在受支持的设备环境中进入 playing 状态。
- 无法播放时能够明确定位失败阶段。
- 来源和媒体 URL 具备可回滚开关。
- 不依赖绕过 DRM、会员或访问控制来达到验收结果。

## Out of Scope

- 本规格不修改四个一级入口和播放器 UI。
- 本规格不恢复客户端 `/song/url/match` 解灰流程。
- 本规格不把 `/auth/downloads` 改造成普通在线播放接口。
- 本规格不承诺所有来源提供主流商业曲库、无损音质或永久有效 URL。
- 本规格不接入 Spotify 或 Apple Music 的受订阅保护内容作为免费直链。
- 本规格不要求用户上传第三方平台 Cookie。
- 本规格不实现绕过 DRM、会员校验、地区访问控制或服务条款限制。
- 本规格不在第一阶段将新来源歌曲永久写入现有仅支持网易云 ID 的客户端模型。
- 本规格不把 yt-dlp 或 Python 进程直接放进 Express 主请求链路。
- 本规格不在没有真实设备反馈的情况下宣称 AVPlayer 兼容性已验收。

## Further Notes

- 当前最重要的工程顺序不是立即增加更多平台分支，而是先建立“解析完成到 AVPlayer playing”的可观测反馈环；否则换源后仍可能无法判断失败发生在哪里。
- 国内多平台方案更可能改善主流中文歌曲覆盖，但其可用性、授权和平台接口稳定性必须单独验收。
- Audius、Jamendo 等开放/授权来源更适合“真正免费且可合规播放”，但不能替代主流商业曲库。
- Meting-API 的缓存和隔离部署可能减少重复请求，但不能保证上游平台永不限流，也不能自动解决来源授权问题。
- 本规格已发布为 GitHub Issue #1，并使用 `ready-for-agent` 标签；后续实现应按阶段拆分为可独立验收的任务。
