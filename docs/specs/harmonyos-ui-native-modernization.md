# 鸿蒙原生 UI 现代化与前端性能重构规格

状态：待评审并就测试接缝（Seams）与用户确认。规格标签：`ready-for-agent`。

## Problem Statement

用户在使用 DreamMusic 播放私人音乐库时，追求的是“静谧克制”的沉浸式听歌体验（The Scene-Tinted Gallery），但当前前端页面在交互细腻度、大曲库性能以及鸿蒙原生质感上存在若干关键痛点：

1. **大曲库滑动掉帧与启动延迟**：随着本地导入歌曲数量增长，音乐库列表渲染存在明显的掉帧和卡顿，长列表所有节点在进入页面时被全量上树创建，内存开销过大，破坏了丝滑流畅的滑动体验。
2. **切页生硬缺乏连贯感**：从底部常驻播放条切换到正在播放全屏页面时，封面与播控信息出现生硬的页面割裂，缺少鸿蒙官方标志性的“一镜到底”共享元素流畅转场，无法建立视觉上下文连接。
3. **播放队列拖拽体验滞后**：在播放队列中调整歌曲顺序时，手势响应偶现迟滞与位置漂移，手写坐标换算丢失了系统级的触觉物理阻尼和重排弹簧动画。
4. **全屏沉浸体验断层**：在具有挖孔屏、状态栏和底部导航手势指示条的现代设备上，背景图未能完全穿透至屏幕物理边缘，顶底避让区出现可见的底色割裂，破坏了“取色于景”的整体画境。
5. **系统大字体与多端适应不足**：字阶硬编码限制了系统字体缩放（动态字体大小）的自适应；在折叠屏与平板等大屏设备展开时，界面仅机械拉伸，未能合理呈现双栏分块布局。
6. **缺乏轻量级自动化 UI 验证机制**：UI 调整与视觉回归依赖重型 DevEco 预览器或手动实机操作，缺乏在终端直接自动化捕获布局层次与页面证据的敏捷闭环。

## Solution

在坚守 ADR-0006 四个一级入口（音乐库、正在播放、队列、我的）和“取色于景”视觉系统的原则下，全面拥抱 HarmonyOS / ArkUI 官方现代 UI 能力与工程工具链：

1. **列表虚拟化与懒加载**：将长列表重构为声明式懒加载数据源模型，仅渲染视口及近邻缓冲项，使歌曲列表在数千首规模下依然保持冷启动秒开与 120Hz 满帧滚动。
2. **一镜到底共享元素转场**：利用隐式共享元素机制，使常驻播放条的小尺寸封面与正在播放页的黑胶唱片在展开与收起时实现几何形态与位置的平滑无缝形变演化。
3. **原生声明式列表拖拽排序**：将队列排序收敛至系统列表原生拖拽与数据移动回调，内置物理阻尼、列表项位移动画与系统触控反馈，大幅精简维护负担。
4. **全贯通沉浸式避让管理**：开启全屏沉浸式窗口，将背景图层拓展至系统状态栏与底部手势区，内容交互区根据避让区域动态内缩，确保视觉无缝且可点按区域绝不被遮挡。
5. **动态字阶与弹性布局**：建立规范的动态字号令牌体系，保障文字在系统动态字号调整下自适应流式排版；为折叠屏与平板预留响应式分栏断点。
6. **CLI 驱动的 UI 自动化验证闭环**：结合本地 `@deveco/deveco-cli` 工具链，建立免开重型 IDE 的自动化 UI 布局树检查、屏幕截图导出及代码规范检验流程。

## User Stories

1. 作为听歌用户，我希望进入几百上千首歌曲的音乐库时界面瞬间加载完毕，以便随时开始选歌。
2. 作为听歌用户，我希望快速划动歌曲列表时始终保持 120Hz 满帧顺滑，以便不错过任何想听的音乐。
3. 作为听歌用户，我希望快速滚动列表时已经滚出视口的封面与卡片自动回收资源，以便应用不会占用过多设备内存。
4. 作为听歌用户，我希望点击底部常驻播放条时，当前封面能够平滑放大并飞入到黑胶唱片正中，以便获得视觉连续性。
5. 作为听歌用户，我希望从正在播放页向下滑动或点击返回时，黑胶唱片能够无缝缩小收回到底部播放条，以便体验连贯自然的交互。
6. 作为听歌用户，我希望在播放队列中拖动歌曲排序手柄时能立即吸附手指，以便快速调整听歌次序。
7. 作为听歌用户，我希望拖拽歌曲时列表其他歌曲能够以平滑的弹簧动画自动腾出位置，以便直观预览插入后的效果。
8. 作为听歌用户，我希望拖拽放下歌曲时能有微妙的系统触觉振动反馈，以便明确感知调整已经生效。
9. 作为听歌用户，我希望正在播放的歌曲在队列中被拖拽到新位置后，播放不会中断，以便保持音乐连续性。
10. 作为听歌用户，我希望在全面屏和挖孔屏手机上，动态取色的背景能够自然延伸到屏幕最顶部和最底部，以便没有突兀的黑边割裂。
11. 作为听歌用户，我希望沉浸式全屏下顶部的曲名、返回键和底部的导航按钮不会与系统状态栏图标或导航指示条重叠，以便所有操作始终清晰易点。
12. 作为听歌用户，我希望在系统设置中调大系统字号时，歌曲标题和信息能相应放大且自动换行，以便视力疲劳时依然清晰阅读。
13. 作为听歌用户，我希望当曲名过长或字号变大时，播放/暂停、上一曲、下一曲核心控制按钮依然保持在舒适的点击位置，以便盲操不被挤乱。
14. 作为听歌用户，我希望正在播放页的播放/暂停大圆按钮在按下时有微妙的收缩下陷反馈，以便明确感知按键响应。
15. 作为听歌用户，我希望正在播放页的歌词窗口上下边缘有柔和的渐隐淡化，以便歌词滚出时过渡自然不突兀。
16. 作为听歌用户，我希望滚动歌词时能有跟手阻尼，松手后过一段合理时间自动恢复高亮行跟随，以便随意翻看歌词不被强行拉扯。
17. 作为听歌用户，我希望在音乐库歌曲条目上向左侧滑时能直接露出“加入歌单”或“收藏”快捷操作，以便省去多层菜单点击。
18. 作为听歌用户，我希望在音乐库专辑和艺术家分类列表中能看到分类首字母吸顶，以便在大曲库中快速定位目标。
19. 作为听歌用户，我希望常驻播放条在歌曲处于缓冲加载中时能有精致的原生加载指示，以便获知音乐状态。
20. 作为听歌用户，我希望通过折叠屏手机展开或平板横屏使用时，音乐库与播放器能够分栏展现，以便充分利用大屏空间。
21. 作为听歌用户，我希望折叠屏半折态放置在桌面上时，上半屏展示封面与歌词，下半屏展示播控器，以便实现悬停免手持听歌。
22. 作为开发者与维护者，我希望能在终端一行命令捕获当前界面截图到验收目录，以便快速做 UI 视觉走查。
23. 作为开发者与维护者，我希望能在终端无缝导出界面的无障碍节点树与坐标信息，以便自动化验证控件可点击性与重叠情况。
24. 作为开发者与维护者，我希望在修改 UI 样式时能通过热重载快速在模拟器或真机呈现，以便免去冗长的全量打包等待。
25. 作为开发者与维护者，我希望代码提交前能通过命令行静态代码检查，以便杜绝不合规的硬编码与性能隐患。

## Implementation Decisions

### 1. 列表数据源虚拟化改造（Lazy Loading Architecture）
- **长列表容器规范**：移除普通列表容器内的全量遍历模式，长列表（音乐库歌曲列表、专辑音轨列表、队列列表）统一接入标准虚拟滚动机制。
- **数据源适配契约**：构建可复用的响应式数据源管理类，封装数据总数查询、指定索引获取以及增量通知机制（包括单项变更、区间刷新、条目移动和整体重置）。
- **预加载缓冲区控制**：列表配置合理的前后视口预加载缓存计数（默认保留 5 项），兼顾高速滑动时的空白占位控制与底层内存消耗平衡。

### 2. 隐式共享元素转场（Implicit Geometry Transition）
- **元素共享契约**：在常驻微型播放条的封面缩略图与正在播放页的黑胶唱片标签之间建立全局唯一的共享几何标识符。
- **转场联动控制**：两端组件必须配合显式属性动画触发（如尺寸、圆角、透明度变化），使 ArkUI 渲染管道自动接管中间帧的插值变换与空间位移。
- **减弱动效降级**：当系统启用“减弱动效”无障碍设置时，自动跳过空间形变动画，优雅降级为淡入淡出，遵循无障碍准则。

### 3. 队列拖拽的原生化收敛（Native Drag & Reorder）
- **剔除自定义手势测算**：彻底废弃手写的触摸坐标采样、边界检测计时器与浮层测算逻辑。
- **原生回调接线**：利用 ArkUI 列表项原生位移回调捕获条目从起始索引到目标索引的变动事件，并直接同步给播放队列核心引擎。
- **事务一致性保护**：拖拽移动事件期间，仅更新数据源的展示顺序；在拖拽动作完全提交离手后，再触发一次持久化落盘，杜绝高频 I/O 阻塞主线程。

### 4. 窗口级全屏沉浸与避让管理（Immersive Window & SafeArea）
- **全屏布局开启**：在应用主窗口加载内容前启用窗口全屏布局属性，使应用视图拓扑完整覆盖包含状态栏与导航条在内的全部物理屏幕区域。
- **背景层拓展策略**：全局背景层（包括深色底板、自定义壁纸图片与蒙层叠加）明确拓展至系统避让区两端边缘，消灭一切边缘缝隙。
- **内容区安全内缩**：交互内容层（顶部标题操作栏、底部导航栏）监听或查询系统窗口规避区域（AvoidArea），通过内边距（padding）进行物理避让，确保在任意挖孔屏或圆角屏下交互热区完全安全。

### 5. 动态字阶令牌与流式排版（Dynamic Type System）
- **字号单位规范**：所有字阶设计令牌从纯数值全面迁移至规范的弹性点（`fp`）语义。
- **弹性文本约束**：核心文本组件统一配置合理的折行规则（如强制断词折行与省略号裁剪模式），避免系统字号调大时引发组件挤压与换行畸形。
- **核心播控区尺寸锁死保底**：关键触控图标（播放/暂停、上一曲、下一曲等）保持固定的最小物理触控热区（不小于 48vp），不受文本动态缩放的挤压。

### 6. 基于 DevEco CLI 的自动化验证流水线
- **无障碍树巡检规范**：利用 CLI 工具导出当前画面的无障碍树，并核验核心控件标签是否包含清晰意图。
- **视觉回归资产捕获**：在主要机型模拟器与真机上，通过 CLI 截图指令自动化采集 4 个一级页面的高保真凭证，持久化至项目质量证据库。

## Testing Decisions

### 核心测试接缝（Seams）

我们建立 **两层最高接缝（Highest Seams）** 来承载本规格的自动化与确定性验收，尽量减少内部组件细枝末节的打桩测试：

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 接缝 1（顶层/系统行为接缝）：DevEco CLI 自动化巡检与布局树验证              │
│ · 外部行为：通过 `devecocli ui layout` 验证屏幕上真实可达的无障碍节点与层级  │
│ · 视觉证据：通过 `devecocli ui screenshot` 捕获多设备形态下的像素证据      │
│ · 静态质量：通过 `devecocli check lint` 验证 ArkTS 规范与性能零警告        │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ 驱动与验证
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 接缝 2（领域/状态模型接缝）：响应式数据源与播放队列引擎契约                │
│ · 外部行为：验证 `IDataSource` 在增删移查时对 UI 发出的原子事件通知        │
│ · 事务契约：验证 `QueueEngine` 在重排、切换与持久化下的状态一致性          │
└────────────────────────────────────────────────────────────────────────┘
```

1. **接缝 1：DevEco CLI 系统级端到端测试接缝（最高缝隙）**
   - **理由**：UI 组件层若单独做单元测试，往往沦为对 ArkUI 内部布局算法的低价值模拟。通过官方 CLI 工具在运行中的设备/模拟器上直接读取无障碍布局树与截屏，可以在最顶层黑盒验证组件是否正确挂载、是否具有无障碍描述、是否存在异常重叠。
   - **验证重点**：
     - 执行 `devecocli ui layout --format json` 验证长列表视口内渲染节点数是否受控（证明懒加载生效，而非数千项全量上树）。
     - 验证拖拽后无障碍节点顺序与播放器实际状态匹配。
     - 捕获状态栏与底部手势条避让区截图，证明沉浸式无缝且无文字穿模。

2. **接缝 2：列表数据源适配器与队列引擎契约接缝（领域模型最高缝隙）**
   - **理由**：避免测试内部 private 变量，仅针对数据源对外的标准监听接口与数据项获取能力进行测试。
   - **验证重点**：
     - 测试当向数据源追加 2000 条音轨时，仅发出正确的批量事件通知，耗时在毫秒级内。
     - 测试在连续拖拽调换歌曲位置时，队列引擎的活动歌曲索引与断点恢复数据精准对应。

### 什么是好的测试
- **仅测试外部可见行为**：验证“用户滑动时看到下一屏数据”、“拖拽后下一首歌变为目标歌曲”、“状态栏下方背景连贯”，绝不测试组件内部声明了几个临时变量或状态计时器。
- **不依赖不可控外部网络**：所有测试使用本地音轨数据和受控 Mock，确保测试结果具备完全确定性。

### 可复用的测试先例
- 工程现有的 SQLite 事务与音轨扫描测试。
- 播放控制状态机（`PlaybackControlGate`）的防抖与竞态安全测试。
- NightDream 与 API 契约的回归测试模式。

## Out of Scope

1. **后端中间层与网络 API 变更**：不涉及 NightDream Express 中间层或网易云 API 架构调整（多源调度由独立规格承载）。
2. **底层数据库表结构重构**：现有的 SQLite 9 张实体表结构保持稳定，不修改既有字段定义。
3. **音频编解码底层替换**：保留现有的 `AVPlayer` 与音频沙箱管理链路，不引入三方原生 C++ 音频软解引擎。
4. **分布式跨端流转协议（Super Device / Cast）**：多设备音视频投播与连续流转留在后续独立特性规划。
5. **复杂歌词逐字动画特效制作**：歌词卡拉OK级逐字精确染色跳动不在本轮基础现代化的交付范围内。

## Further Notes

- 本规格严格遵守 **ADR-0006**，四个一级入口（音乐库、正在播放、队列、我的）的产品信息架构保持完全不变。
- 本规格严格维护 **DESIGN.md** 的核心承诺——“取色于景（The Scene-Tinted Gallery）”，所有优化均在加强沉浸感与质感，杜绝任何喧宾夺主的浮夸霓虹装饰。
- 本规格的各项任务遵循渐进式发布原则，在测试接缝得到验证后，可分批合入主干：
  - **里程碑 1**：全屏沉浸式与安全区修复 + 长列表虚拟化（攻克核心性能与视觉底色缺陷）。
  - **里程碑 2**：队列原生拖拽替换 + 正在播放一镜到底转场（补齐核心交互质感）。
  - **里程碑 3**：字阶动态适配 + 规范化 CLI 自动化测试用例固化。
